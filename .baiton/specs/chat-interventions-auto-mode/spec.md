# OVERVIEW

Extend the Baiton Chat_View so every point where a human is needed — an orchestrator question, an orchestrator confirmation (today the modal `ConfirmSeam` behind `approve_spec`/`draft_spec`), and a sub-agent harness permission ask or question — surfaces as one inline, interactive intervention card in the conversation and is answered in place, and add an Auto mode toggle (left of Stop) that lets an allow-list plus the orchestrator model auto-approve safe asks while escalating the rest onto the same cards.

Architecture, following the existing host-free-core / activation-glue split:

1. Intervention core (`src/orchestrator/interventions.ts` + `seams.ts`). A single `Intervention` shape with kinds `question` (options or free text), `confirm`, and `permission` (a harness ask carrying agent/tool/args), a pure pending-ask registry (create / resolve / reject / rejectAll) and an `InterventionSeam.ask()` that resolves with the user's answer. The existing `ConfirmSeam` is kept as an adapter over the new seam so `approve_spec`/`draft_spec` and the control tools keep compiling; the chat wiring replaces the `showWarningMessage` modal with the inline path. Answering resumes the originating flow on the seam that created the ask; Stop (or reject) resolves every pending ask as declined so control always returns to the user.

2. Protocol + persistence. `webviewProtocol.ts` gains `RenderRecord.intervention` (pending or resolved card state), `HostToWebview` messages `showIntervention` / `resolveIntervention` / `setAutoMode`, `WebviewToHost` messages `answerIntervention` / `setAutoMode`, and an `autoMode` flag in `WebviewState`; `reduce` stays pure and exhaustively tested. Intervention records are persisted to the session transcript (`TranscriptRecord.intervention`) so resolved cards remain an inline record and survive conversation switching, reload and re-render; `toRenderRecords` projects them. `media/protocol.js` mirrors the reducer and, because no parity test exists for it today, a shared-fixture mirror test (`test/fixtures/protocolCases.ts` + `test/webviewProtocol.mirror.test.ts`, modelled on `test/configPanel.mirror.test.ts`) pins TS and JS `reduce` to identical output.

3. Webview. `media/chat.js` renders cards from `record.intervention`: buttons/radio for option questions, a text input for open answers, Approve/Decline for confirms and permission asks, and a settled state showing the decision, rationale and (for escalations) the "what you are approving / why it was flagged" description. The composer's control row gains the Auto toggle immediately left of Stop; it stays enabled while busy (a pipeline running) so it can be flipped mid-run.

4. Orchestrator question tool. A new `ask_user` control tool (both phases, non-mutating, non-dispatch) lets the model ask an option or free-text question through the seam and receives the answer as its tool result; the system prompt tells the model when to use it instead of ending the turn with a question.

5. Auto mode core (`src/orchestrator/autoMode.ts`). A pure two-stage gate: (a) a deterministic per-agent always-approve allow-list (derived from the existing adapter permission data — claude's `--allowedTools` sets, opencode's agent permission rules, the role profile's shell/write bits) that approves matching asks with no round-trip; (b) for everything else, a model evaluation through the injected `ModelClient` that returns `approve` with a one-line rationale or `escalate` with a concise what/why-flagged description. Every auto-approval and every escalation is appended to the transcript as an auditable record. The toggle persists across sessions in `workspaceState`, and only asks that arrive while it is on are gated.

6. Harness relay (claude-first, per-adapter probing). A host-free ask-relay file protocol (`src/engine/askRelay.ts`): a launched run's `.baiton/runs/<run-id>/asks/<ask-id>.json` is the ask, `<ask-id>.response.json` the answer. The `LaunchRequest` gains an optional relay descriptor so each adapter can wire its CLI's native hook/delegate-permission mechanism to that location (Claude Code permission hooks first), with the config-driven permission layer as fallback. Separate todos probe claude, opencode, antigravity/agy and codex, record verified findings in the README, and only ship behaviour for surfaces the probe verified. A `vscode`-backed watcher on the run's `asks/` directory routes asks into the chat as `permission` cards on the run's spec conversation, applies Auto mode, and writes the response back; the run stays paused until then. Adapters without native relay use the fallback and the README table states which relay each adapter uses.

Testing follows the repo conventions (mocha + ts-node under `test/`, host-free): reducer, projection, pending-ask registry, `ask_user`, allow-list gate, model evaluator, ask-relay parsing and the protocol mirror are all unit-tested without a VS Code host; controller behaviour is tested against the fake `ChatWebview` surface as `chatController` already is.
