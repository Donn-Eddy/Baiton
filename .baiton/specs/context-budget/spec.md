# OVERVIEW

Make the chat orchestrator context-aware: it knows the selected model's context window, knows how many tokens the next request will carry, shows both in the chat, and compacts the conversation — trim first, then summarise — before the endpoint has to refuse it. Scope is the chat orchestrator's own request payload (`runToolLoop` in `src/orchestrator/toolLoop.ts`); the sub-agent Briefs are out of scope. The transcript file stays append-only and complete: compaction changes what the model is sent, never what the user can read back.

**Why now (diagnosis, 2026-09-30).** Investigation `investigate-20260930-000333-ndmz` confirmed the loop re-sends the whole transcript every round with no token accounting, no pruning and only a 64 KiB per-read cap. The Baiton output channel shows two distinct failure classes: (a) `HTTP 400 context_length_exceeded` from DeepInfra with payloads of 1.7M and 4.3M tokens on 2026-09-29 (unbounded non-read tool results — one chat transcript is 100 MB); and (b) three `HTTP 400` with an EMPTY body at 00:01:53, 00:02:48 and 00:05:26 on 2026-09-30 for a 100K-token conversation on a 1M window. Class (b) is a replay defect, not size: `toChatMessage` in `src/activation/chatController.ts` turns every persisted intervention card (an `ask_user` question, written as a `system` record while the tool call is still open) into a standalone `assistant` message, so a reloaded history reads `assistant(tool_calls) → assistant("[intervention] …") → tool`. In-memory history never contains the card, which is why the first turn works and every later turn of a conversation that used `ask_user` is rejected by strict OpenAI-compatible endpoints. Both classes are fixed here.

**Replay correctness — `src/orchestrator/transcriptReader.ts`, `src/activation/chatController.ts`.** Move the record→message conversion out of the controller into a host-free `toHistory(records: TranscriptRecord[]): ChatMessage[]` beside `readTranscript`. Rules: a `tool` record always directly follows the assistant record carrying its call (an intervention record met while a call window is open is deferred until the window's last `tool` record has been emitted); a pending+settled pair for the same intervention id collapses to the settled card; an intervention replays as one `assistant` message `[intervention] <prompt>\nDecision: <answer>` exactly as today; a persisted `system` record without an intervention still replays as `assistant`. `loadHistory` calls `toHistory`. Tests: a transcript shaped like the 2026-09-30 failure yields no message between an assistant `tool_calls` entry and its `tool` messages; a property test over random valid transcripts asserts every `tool` message is adjacent to its call.

**Bounded tool results — `src/orchestrator/toolLoop.ts`, `src/orchestrator/guard.ts`.** Every tool result the loop appends is bounded, not only reads: `TOOL_RESULT_CAP_BYTES = 64 * 1024` (exported from guard beside `READ_RESULT_CAP_BYTES`) and a `boundToolResult(text)` helper that truncates on a UTF-8 boundary and appends a one-line `[truncated: <n> of <m> bytes]` note. `toolResultContent` applies it to success and error content alike. The capped content is what is appended to history AND persisted, so the transcript can no longer grow to 100 MB.

**Model limits — `src/orchestrator/modelCatalog.ts`, `src/orchestrator/modelsDev.ts`, `src/activation/modelDiscovery.ts`, `package.json`.** `ModelEntry` gains optional `contextWindow?: number` and `maxOutput?: number`. The models.dev mapping already parses `limits.context`/`limits.output` into `FeedModelLimits`; carry them onto every entry derived from the feed (including the Claude adapter's feed fallback); other sources leave them undefined. New setting `baiton.orchestrator.contextWindow` (integer, default 0 = unset) is the user fallback. A host-free `resolveContextWindow(entry: ModelEntry | undefined, configured: unknown): number | undefined` in the new `src/orchestrator/contextBudget.ts` returns catalog first, setting second, `undefined` when neither is known. The catalog memento round-trips the two new fields.

**Token accounting — `src/orchestrator/contextBudget.ts` (new, no `vscode` import), `src/orchestrator/modelClient.ts`, `src/orchestrator/copilotClient.ts`.** `CompletionResult` gains optional `usage?: { promptTokens: number; completionTokens: number }`. `OpenAiModelClient` fills it from the non-streaming `usage` object and, when streaming, from any SSE event carrying `usage` (the parser keeps the last one seen); it sends `stream_options: { include_usage: true }` when streaming unless the new setting `baiton.orchestrator.usageInStream` (boolean, default true) is off, for endpoints that reject the field. `CopilotModelClient` leaves `usage` undefined. `estimateTokens(text: string): number` is the local fallback (`ceil(bytes / 4)`), `estimateMessages(messages, tools)` sums content, tool-call arguments, tool schemas and a fixed per-message overhead. `ContextTracker` (one per conversation, owned by the controller) records after each completion `loaded = usage.promptTokens` when present, else `estimateMessages` of what was sent, and exposes `status(): ContextStatus { loaded: number; window?: number; source: 'usage' | 'estimate'; ratio?: number }`.

**Trim (lossless first) — `src/orchestrator/contextTrim.ts` (new, pure).** `trimHistory(history: ChatMessage[], opts): ChatMessage[]` operates on the payload for one round only; the transcript is untouched. In this order, oldest first, until the estimate is under the soft threshold: (1) drop replayed intervention lines whose card was auto-approved (`auto: true`, the "old auto-approved tool calls"); (2) replace `tool` results that belong to earlier turns — every turn except the current one and the one before it — with the stub `[trimmed <tool> result: <m> bytes; call <id>]`, keeping `tool_call_id` and the assistant `tool_calls` entry so pairing is intact; (3) replace remaining large `tool` results in the current turn older than the last two rounds the same way. Trim runs whenever `ratio` exceeds `baiton.orchestrator.contextTrimAt` (number, default 0.5) and the window is known; with an unknown window it runs only on the manual command. `runToolLoop` gains an optional `budget?: ContextBudget` seam (`prepare(history): ChatMessage[]` and `observe(sent, completion): void`) so the loop stays host-free and the existing tests are unchanged when the seam is absent.

**Summarise (lossy second) — `src/orchestrator/chatTranscript.ts`, `src/orchestrator/transcriptReader.ts`, `src/activation/chatController.ts`.** When the estimate is still above `baiton.orchestrator.contextSummarizeAt` (number, default 0.8) after trimming, or on the manual command, the controller asks the active client for a text-only completion (no tools, like the auto-mode evaluator) that summarises every message older than the last two turns into: goals, decisions taken, files touched, open questions. The result is appended to the transcript as a record `{ role: 'system', content: <summary>, compaction: { id, fromTs, toTs, messages: n } }`. `toHistory` honours compaction records: records with `ts` in `[fromTs, toTs]` are skipped and the summary is emitted once as an `assistant` message `[context summary] …` in their place; the view still renders the full transcript. The compaction record round-trips through `readTranscript`'s structural checks. A failed summary completion is surfaced inline and leaves the conversation as it was.

**Meter and manual command — `src/orchestrator/webviewProtocol.ts`, `media/chat.html`, `media/chat.js`, `src/activation/chatController.ts`, `src/activation/commands.ts`, `package.json`.** New outbound `{ type: 'setContextUsage'; loaded: number; window: number | null; source: 'usage' | 'estimate' }` posted after every completion and after every compaction, rendered as a compact line under the composer (`~256K / 1M · usage` or `~256K · window unknown`) with a **Compact** button; inbound `{ type: 'compactContext' }` and command `baiton.compactContext` run trim-then-summarise on the conversation in view, refused while busy. The mirror and reducer tests cover the new messages.

**Pre-flight instead of HTTP 400 — `src/orchestrator/toolLoop.ts`, `src/activation/chatController.ts`.** Before each completion, when the window is known and the estimated payload exceeds `window − reserve` (reserve = configured `max_tokens`, else `maxOutput`, else 8192), the budget seam trims, then summarises, then re-estimates; if still over, the loop appends the notice `The conversation exceeds the model's context window (~N of W tokens); compact it or start a new chat.` and stops without calling the endpoint. `UnreachableEndpointError` for a 4xx with an empty body reads `endpoint returned HTTP 400 (empty body; payload ~N tokens)` so the class-(b) failure is diagnosable from the Baiton channel alone.

**Constraints.** No `vscode` import enters `src/orchestrator/`; the transcript file format stays backward compatible (old files load unchanged, new `compaction` records are ignored by older readers because `intervention`-less `system` records already replay); no new runtime dependency; `runToolLoop` without a `budget` seam behaves byte-for-byte as today. Tests are mocha under `test/`; `npm run compile`, `npm run lint` and `npm test` stay green after every todo.
