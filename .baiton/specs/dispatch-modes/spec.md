# OVERVIEW

Give each Baiton chat conversation an explicit mode — Spec (the default, unchanged), Bug, Quick, Refactor and Investigate — and use it to pick the pipeline. Spec keeps today's gather → `draft_spec` → approve → `run` per todo flow byte-for-byte: `buildSystemPrompt`/`phaseFor` gain an optional trailing `mode` argument whose absence (or `spec`) reproduces the current prompt, phases and tool surface, so existing Spec-mode tests stay untouched. Bug, Quick and Refactor share one spec-less pipeline that differs only in the framing handed to the planner and executor; Investigate is a distinct read-only dispatch that ends in a written finding. No non-Spec run ever writes under `.baiton/specs/`; everything it owns lives under `.baiton/runs/<run-id>/` (already gitignored) and `.baiton/worktrees/<run-id>/` (newly gitignored).

Architecture, following the repo's host-free-core / activation-glue split:

1. Vocabulary (`src/model/mode.ts`, `src/model/stage.ts`, `src/schema/*`). `RunMode = 'spec' | 'bug' | 'quick' | 'refactor' | 'investigate'` with `DEFAULT_MODE = 'spec'` and an `isSpecless(mode)` predicate. A new `investigate` stage joins `STAGES`; it is run by the existing `reviewer` role (read + shell, run-dir writes only), so the config `roles` mapping, `defaultConfig` and the role profiles are unchanged and no config migration is needed. `investigateSchema` (`finding`, `files`, `next_steps`) is added beside the other stage schemas, `persistencePathForStage('investigate')` yields `finding.md`, and `renderArtifact` gets an investigate renderer. Every existing stage's schema, path and renderer stays identical.

2. Run store (`src/engine/runStore.ts`, host-free). One manifest per run at `.baiton/runs/<run-id>/run.json`: id, mode, the composer's selected mode plus an `explicitMode` flag when the orchestrator proposed a different one, the one-line statement, guessed files, optional reproduction, base branch and its head commit at start, branch (`baiton/<mode>/<run-id>`), worktree dir, state (`confirmed | planning | planned | executing | executed | reviewing | done | failed | cancelled | answered | merged`), attempt counters, outcome (review verdict, or the finding for Investigate), timestamps. Each stage launch inside a run uses the launch id `<run-id>.<stage>.<n>` so `launchStage`'s `.baiton/runs/<launch-id>/brief.md|result.json|asks/` layout and the role profiles' run-dir grants are reused unchanged; the run's own journal is `.baiton/runs/<run-id>/runs.jsonl` (the run id stands in for `todoId`, as the spec draft already does with the slug) and rendered artifacts (`plan.md`, `execute-<n>.md`, `review-<n>.md`, `finding.md`) land in the run dir through an `ArtifactWriter` override, never under a spec.

3. Git (`src/git/types.ts`, `src/git/gitService.ts`, `src/engine/runWorktree.ts`). The service gains worktree add/list/remove, branch delete, `branchHead(ref)`, `merge(branch, message)` and a whole-tree `isClean()`. `runWorktree.ts` composes them: create `.baiton/worktrees/<run-id>/` on `baiton/<mode>/<run-id>` from the head of the branch checked out when the run started; merge refuses with a named reason when that base branch has moved since the run started (`base-moved`), when the working tree is dirty (`dirty-tree`), or when the checked-out branch is not the base branch (`wrong-branch`); a successful merge removes the worktree and branch. A `GitService` bound to the worktree dir (`createGitService(worktreeDir)`) performs the run's own head/branch/commit/diff calls. `GITIGNORE_CONTENTS` gains `/worktrees/`.

4. Launcher (`src/engine/launcher.ts`). `LaunchStageInput` gains an optional `cwd` (the run root): the terminal cwd and the `.baiton/runs/<launch-id>/` brief/result/asks directories resolve under it, so a stage launched into a worktree keeps relative run-dir grants correct. Absent, the launch is byte-identical to today.

5. Run briefs (`src/engine/runContext.ts`, pure, modelled on `stageContext.ts`). Per mode and stage: a `# Run` section (mode, statement, files, target branch); Bug adds `# Defect` and `# Reproduction`; Quick carries the statement and guessed files; Refactor adds behaviour-preservation emphasis and the configured `git.verify` command that must stay green; execute retries carry the latest review; review carries the execute summary and commit; Investigate carries the question and files. `buildBrief` selects the investigate instruction text by stage while every existing role's text is unchanged.

6. Run pipeline (`src/engine/runPipeline.ts`, host-free, modelled on `specDraft.ts`). `start(confirmedRequest)` writes the manifest, creates the worktree, then drives `plan → execute → review` with the existing `launchStage`/`awaitStageResult`/journal machinery; a `findings` verdict sends the run back to `execute` (bounded by `limits.exec_attempts`), `pass` marks it `done`; Execute commits in the worktree with the `Run-Id:` trailer after the same HEAD/branch drift check the queue performs. Investigate runs one `investigate` stage from the checkout with no worktree, commit or diff and marks the run `answered`. `cancel()` disposes the running terminal, records `cancelled`, and leaves the worktree and branch in place. The pipeline honours the one-stage-per-repository guarantee from both sides: it refuses `busy` while any spec queue or the spec draft is running, and `RunQueueDeps.isExternallyBusy` is widened to include it. It emits change events the Runs view and chat subscribe to.

7. Orchestrator (`guard.ts`, `controlTools.ts`, `seams.ts`, `toolServices.ts`, `systemPrompt.ts`). `OrchestratorPhase` gains `run`. The read tools and `ask_user` are advertised in `run`; two new dispatch tools live only there: `start_run(mode, statement, files, reproduction?)` and `investigate(question, files)`. Each raises the confirm card (mode, one-line statement, guessed files, target branch) through the intervention seam, dispatches through a new `RunPipelineSeam` and returns as soon as the run is launched (like `draft_spec`); a decline writes nothing and dispatches nothing. `draft_spec`, the todo tools, `approve_spec`, `run` and `submit_pr` keep their phases, so they are unavailable in a non-Spec conversation and the guard's Restricted-Mode rule disables the new tools like every other dispatch tool. The system prompt for a run-mode conversation replaces the spec flow text with the mode's flow (inspect with read tools, state the work and guessed files, call the run tool; propose a different mode through `ask_user` when warranted) while the Spec prompt is untouched.

8. Chat mode control (`webviewProtocol.ts`, `media/protocol.js`, `media/chat.html`, `media/chat.js`, `chatController.ts`, `commands.ts`). New `setMode` messages in both directions and a `mode` field in `WebviewState`, plus a host→webview `setRunActive` flag; `media/protocol.js` mirrors the reducer and the shared-fixture parity test pins them. A `Mode` select sits in the composer beside the Auto toggle, host-authoritative: the change posts `setMode` and the control repaints only on the host's echo. It is disabled while the chat is busy or a run is in flight, and pinned to Spec on a spec conversation (the mode is a property of the Workspace conversation; a spec conversation is always Spec). The selection is remembered in `workspaceState` (`baiton.chat.mode`), never `settings.json`. The controller picks the phase, tools and prompt per mode, posts a system note when a run completes, and after an Investigate finding lands posts a promote card (Bug / Quick / dismiss) whose choice raises the run confirm card with the finding as the work statement.

9. Runs view (`src/model/runTreeModel.ts`, `src/activation/runsExplorer.ts`, `package.json`). A tree view `baiton.runsView` beside the Spec Explorer with two groups: Active (mode, statement, branch, current stage; Cancel while a stage is running) and Complete (mode, statement, branch, outcome — verdict, cancelled/failed, or "answered" for Investigate; View diff and Merge into `<base branch>`). Nodes are built by a pure model from the manifests with `contextValue` tokens the `view/item/context` `when` clauses match, refreshed by a watcher over `.baiton/runs/*/run.json` and the pipeline's events. Commands `baiton.runs.cancel`, `baiton.runs.viewDiff` and `baiton.runs.merge` are gated on `!baiton.restricted` where they act.

Testing follows the repo conventions (mocha + ts-node under `test/`, host-free, temp git repos for git behaviour, fakes for adapters/terminals as in the run-queue and spec-draft tests). Every existing test passes unchanged; Spec-mode acceptance tests are not modified; new behaviour gets its own test files, including an end-to-end spec-less pipeline test modelled on `test/integration.plan-execute-review.test.ts`.
