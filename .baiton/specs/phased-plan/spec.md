# OVERVIEW

## Endstate

Baiton presents itself, and is built, as a phased-plan tool. The drafting step produces `.baiton/plans/<slug>/plan.md`: a preamble with three sections (Endstate, What needs changing, Limitations & constraints) followed by a `# PHASES` list of `P##` phases. Each phase keeps today's todo lifecycle (`pending`...`done`) and is planned, executed, reviewed and landed on its own worktree branch. Every identifier, tool name, mode id, role, stage, command/view id, path, commit prefix, user-facing string, test name and README passage that says "spec" or "todo" now uses plan/phase vocabulary. The one exception is the legacy compatibility code: existing `.baiton/specs/<slug>/spec.md` documents (`# OVERVIEW`, `# TODOS`, `T##`, `todos/<id>/` artifacts), a `spec-writer` key in `.baiton/config.json`, and persisted sessions whose mode is still `spec`. All of these keep listing, parsing, validating and running unchanged. Quick Fix and Investigation dispatch exactly what they dispatch today.

## What needs changing

- **Document model (`src/model/`).** The parser, validator, writer and hash handle two document kinds:
  - **plan**: preamble sections, then `# PHASES`, with `P##` ids.
  - **legacy spec**: `# OVERVIEW`, then `# TODOS`, with `T##` ids.

  The parsed model records its kind. Its preamble text replaces `overview` as the hashed prose, so approval hash and input rev work the same way for both kinds. A line with the wrong id prefix for its document's kind is malformed, never silently accepted. Type and function names are renamed: `ParsedSpec`→`ParsedPlan`, `Todo`→`Phase`, `TodoState`→`PhaseState` (todoState.ts→phaseState.ts), `todoActions`→`phaseActions`, `specActions`→`planActions`, `parseSpec`/`writeTodoState`→`parsePlan`/`writePhaseState`, and the tree model.
- **Vocabulary ids.** Role `spec-writer`→`plan-writer`. Stage `spec-draft`→`plan-draft`. Mode `spec`→`plan`, with composer labels **Phased Plan** and **Quick Fix**. `isSpecless`→`isPlanless` (or equivalent). Agent name `baiton-plan-writer`. Draft schema `specDraftSchema`→`planDraftSchema`.
- **Config.** `loadConfig` accepts a legacy `roles.spec-writer` entry and maps it onto `plan-writer`; `plan-writer` wins when both exist. `defaultConfig` writes `plan-writer`.
- **Storage and paths.** One document-location resolver serves both `.baiton/plans/<slug>/plan.md` and legacy `.baiton/specs/<slug>/spec.md`, and derives the artifact directory (`phases/<id>/` or `todos/<id>/`) from the document's kind. The store, lister, journal, branch writer (commits `plan(<slug>): …` and stages only that document's directory), `persistencePathForStage`, resultFlow, submitPr, initialize and gitignore all go through it. New writes go only under `plans/`. The legacy files are renamed: `specStore`→`planStore`, `specLister`→`planLister`, `specBranchWriter`→`planBranchWriter`.
- **Engine.** `todoWorktree`→`phaseWorktree`, plus runQueue, transitions, stageContext, recovery, runPipeline, launcher and runContext. Identifiers are renamed and logic is unchanged. Phase branches live under a new namespace (`baiton-phase/<slug>/<id>`); legacy specs keep `baiton-todo/<slug>/<id>` so in-flight branches still resolve. The land commit becomes `plan(<slug>): land <id>`.
- **Drafting.** `specDraft`→`planDraft` writes only `.baiton/plans/<slug>/plan.md`. The plan-writer brief and result schema produce `endstate`, `changes` and `constraints` plus a dependency-ordered phases list, which the extension numbers `P01`, `P02`, …
- **Orchestrator.** The tools become `draft_plan(slug, request)`, `approve_plan`, `land_phase(slug, phase)`, `run(slug, phase, stage)`, `add_phase`, `edit_phase` and `remove_phase`. `update_overview` keeps its name and edits the preamble. The guard protects both document roots. Registry, readTools, toolServices, seams, autoMode and subAgent are updated. In the system prompt, the gather flow becomes: inspect the repo, ask clarifying questions, restate the change as endstate / what needs changing / limitations & constraints, revise until the user agrees, then call `draft_plan`. The orchestrator still never proposes phases itself.
- **Activation/UI.** Spec Explorer→Plan Explorer (`baiton.planExplorer`) lists both roots. `package.json` command titles, views and menus change (Approve Plan, Plan/Execute/Review/Re-plan Phase), as do chatController, engineFacade, extension.ts, sessionStore (a persisted mode `spec` loads as `plan`), webviewProtocol and the `media/` chat UI labels.
- **Tests and README.** Test files and suites are renamed to match the new names. New tests cover both document kinds and both config role keys. The README is rewritten in phased-plan terms.

## Limitations & constraints

- Behaviour must not change in these areas:
  - the state machine, transition table, guards, recovery and journaling;
  - the approval gate: `approve_plan` creates `baiton/<slug>` from the resolved base commit and records `base`, `base_commit`, `branch`, `status: approved` and `approved_rev`, and planning still requires approved plus unblocked;
  - frontmatter key names and the `status`/`mode` value sets;
  - worktrees, verify, the PR stage, the run queue, sub-agent chats, interventions and the usage view;
  - the `baiton/<slug>` branch name.
- Quick Fix still uses `.baiton/runs/` and `.baiton/worktrees/` and writes no plan document. Investigation is untouched.
- Name collisions to handle deliberately:
  - The existing `planner` role and `plan`/`plan-review` stages stay as they are; the new role and stage are `plan-writer` and `plan-draft`.
  - A phase's planner output stays at `phases/<id>/plan.md`, which is distinct from the document `plan.md` at the slug root.
  - The orchestrator's existing internal conversation "phase" (`gather`/`drive`/`run` in systemPrompt.ts and its `systemPrompt.phase.property.test.ts`) must be renamed (for example to conversation step) so "phase" means only a plan phase.
- A slug that exists under both `plans/` and `specs/` needs one defined resolution rule: prefer `plans/` and never write to `specs/`.
- Each phase must leave `npm run compile`, lint and the full test suite green. Because of that, a rename lands together with every caller it touches, and every test it touches is renamed with it.
- The acceptance sweep for "spec"/"todo" has to look at word matches, not raw substrings: "inspect", "special" and "specifier" are fine. Historical comment references such as `(T08)` or `spec "Config Panel"` must be reworded. Legacy compatibility branches may keep the old words, and each one should be clearly marked as legacy.
- Document data already under `.baiton/specs/` in this repository is legacy data and is not migrated.
