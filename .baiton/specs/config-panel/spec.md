# OVERVIEW

# Config Panel

A `Baiton: Open Config Panel` command (`baiton.openConfigPanel`) opens a new `vscode.WebviewPanel` in the editor area that renders `.baiton/config.json` as a structured form (roles, limits, git), validates edits inline, and saves valid JSON back to the file while preserving keys the form does not manage (`version`, `pr`, `git.verify`, any unknown keys). A successful save also applies the new values to the running extension in place (hot-reload), without requiring a window reload.

## Live config reload

Saving is not just a file write: the panel triggers a `refreshConfig` step so the running extension picks up the new values immediately where feasible. The config object is treated as a replaced whole (the freshly parsed document) rather than mutated field by field. Places that hold only `activationState.config` update cheaply; modules that captured derived values at activation (adapter registry, effort/model resolution, spec explorer banners, git settings) are refactored to read config lazily or be re-initialized from the new config object on refresh. Anything that genuinely cannot change at runtime (e.g. citing the loaded config verbatim) is listed and acknowledged; in no case does save require a window reload.

## How it fits the existing code

- **Webview pattern.** Mirrors the chat webview: a static shell `media/config.html` with `${nonce}`/`${cspSource}`/`${baseUri}` placeholders, a strict CSP, `localResourceRoots` limited to `media/`, VS Code theme CSS variables, and a plain-script `media/config.js` (no framework, no new dependencies). The host side is a new activation module `src/activation/configPanel.ts` that owns the panel lifecycle (create-or-reveal singleton, `retainContextWhenHidden`, dispose) and the message channel, structured like `chatWebview.ts` + `chatController.ts`: thin `vscode` glue around a host-free controller.
- **Host-free core in `src/config/`.** All logic that can be unit-tested without a VS Code host lives in a new `src/config/configPanel.ts`: the typed message protocol (`ConfigPanelHostToWebview` / `ConfigPanelWebviewToHost`, e.g. `load`, `loaded`, `loadFailed`, `save`, `saved`, `saveFailed`, `externalChange`, `reset`), the editable form model (`ConfigForm`: six role entries with agent/model/effort, three limits, git remote/base), `formFromConfig`, `validateConfigForm` (per-field errors keyed by a path such as `roles.executor.agent` or `limits.exec_attempts`), and `applyFormToDocument(rawDoc, form)` which merges the edited sections into the raw parsed JSON object so untouched keys survive. Validation rules reuse `LIMIT_BOUNDS` (integer, min/max), `ROLES` from `src/model`, and the installed agent ids from `createAdapterRegistry().ids` (`src/adapter/index.ts`) so the agent dropdown and the validator share one source of truth. Effort options are `low` / `medium` / `high`; a saved value outside that set is shown as an extra option so an existing config still round-trips.
- **Document I/O with conflict detection.** A small `src/config/configDocument.ts` reads the raw file (text + parsed object + a conflict token derived from the file content, e.g. a sha256 of the text via `src/model/hash.ts` conventions or `crypto`) and writes atomically by reusing/exporting the existing `writeJsonAtomic` from `loadConfig.ts`. Save takes the token the panel loaded with; if the on-disk token differs the host refuses with a `conflict` error and the webview offers Reload / Overwrite. A `vscode.workspace.createFileSystemWatcher` on `.baiton/config.json` (same pattern as `specExplorer.ts`) posts `externalChange` so the panel can reload (automatically when the form is pristine, with a banner when it has unsaved edits).
- **Missing or corrupt config.** `loadConfig` already classifies `absent` / `unparseable` / `missing-section` / version errors; the panel reuses it for the semantic check but reads the raw document itself so it can preserve unknown keys. On `absent` or `unparseable` the webview renders an error state with the message and a **Reset to defaults** button that writes `defaultConfigJson()` (from `src/config/defaultConfig.ts`) after a modal confirmation, then reloads the form. Because `activate` in `src/extension.ts` returns early when the config is invalid, the command is registered unconditionally alongside `baiton.initialize` (before the config gate) so the reset path is reachable exactly when it is needed; it resolves the workspace the same way `runInitialize` does.
- **Save semantics.** The webview validates on every input and again on Save; the host re-validates the posted form (the webview is untrusted) before writing. Written JSON is two-space indented with a trailing newline, matching `defaultConfigJson()`. After a successful write the host applies the config live (see Live config reload above) and reports the outcome in the panel; where a component could not hot-reload, the post-save message names it instead of asking for a full Reload Window.
- **Command registration.** `package.json` gains the command (category Baiton, title "Open Config Panel") with no `when` clause (it must work before activation succeeds); `src/activation/commands.ts` exports a `registerConfigPanelCommand` next to `registerInitializeCommand`, and `extension.ts` registers it before the config load.

## Testing
Host-free tests under `test/` (mocha + ts-node, existing conventions): validation and preservation of unknown keys (`test/configPanel.*.test.ts`), document I/O round-trip and conflict detection against a temp dir, and a controller test driven through the `test/fixtures/vscodeLoader.mjs` fake in the style of `test/setApiKey.test.ts` covering load → edit → save, reject-invalid, and reset. `media/config.js` mirrors the pure validator from the TS core the way `media/protocol.js` mirrors `webviewProtocol.ts`; keeping them in sync is asserted by a test that runs the same fixtures through both. Live-reload tests assert that after a save the shared config state and re-initialized consumers reflect the new values without a window reload, and that genuinely non-reloadable factors are reported in the save outcome.
