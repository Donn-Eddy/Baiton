# OVERVIEW

# Config Panel

A `Baiton: Open Config Panel` command (`baiton.openConfigPanel`) renders `.baiton/config.json` as a structured form (roles, limits, git) in a **regular sidebar webview view** — the bottom collapsible section of the Baiton view in the Spec Explorer's left column, below the spec list — validating edits inline and saving valid JSON back to the file while preserving keys the form does not manage (`version`, `pr`, `git.verify`, any unknown keys). A successful save also applies the new values to the running extension in place (hot-reload), without requiring a window reload.

## Live config reload

Saving is not just a file write: the panel triggers a `refreshConfig` step so the running extension picks up the new values immediately where feasible. The config object is treated as a replaced whole (the freshly parsed document) rather than mutated field by field. Places that hold only `activationState.config` update cheaply; modules that captured derived values at activation (adapter registry, effort/model resolution, spec explorer banners, git settings) are refactored to read config lazily or be re-initialized from the new config object on refresh. Anything that genuinely cannot change at runtime (e.g. citing the loaded config verbatim) is listed and acknowledged; in no case does save require a window reload.

## How it fits the existing code

- **Sidebar WebviewView, not a standalone panel.** The panel is a contributed view: `contributes.views` (and a Baiton `contributes.viewsContainers`) in `package.json`, registered via `vscode.window.registerWebviewViewProvider`, hosted on a `vscode.WebviewView` whose visibility VS Code manages — **no create-or-reveal `WebviewPanel` singleton**. The host side is a new activation module `src/activation/configPanel.ts` structured like `chatWebview.ts` + `chatController.ts`: thin `vscode` glue around a host-free controller, with `media/config.html` (nonce CSP, theme variables, `localResourceRoots`) and plain-script `media/config.js` (no framework, no new dependencies). The form renders as the **bottom collapsible section** of the view, under the spec list. `Baiton: Open Config Panel` **reveals** this view; it stays registered unconditionally before the config gate so it works with an absent or corrupt config (the reset path is reachable exactly when needed).
- **Host-free core in `src/config/`.** All logic that can be unit-tested without a VS Code host lives in a new `src/config/configPanel.ts`: the typed message protocol (`ConfigPanelHostToWebview` / `ConfigPanelWebviewToHost`, e.g. `load`, `loaded`, `loadFailed`, `save`, `saved`, `saveFailed`, `externalChange`, `reset`), the editable form model (`ConfigForm`: six role entries with agent/model/effort, three limits, git remote/base), `formFromConfig`, `validateConfigForm` (per-field errors keyed by a path such as `roles.executor.agent` or `limits.exec_attempts`), and `applyFormToDocument(rawDoc, form)` which merges the edited sections into the raw parsed JSON object so untouched keys survive. Validation rules reuse `LIMIT_BOUNDS` (integer, min/max), `ROLES` from `src/model`, and the installed agent ids from `createAdapterRegistry().ids` (`src/adapter/index.ts`) so the agent dropdown and the validator share one source of truth.
- **Source → Model → Effort capability catalogue.** A per-agent table exported from `src/adapter/index.ts`, e.g. `agentCapabilities(): Record<AgentId, { models: readonly string[]; efforts: readonly string[]; modelLink?: string }>`, drives the model and effort dropdowns **and** the host-side validator — one source of truth per the adapter-ids seam. For **claude**, **antigravity (agy)** and **codex** the model list is a curated, hard-coded set rendered as a dropdown **plus an always-present "Other…" entry** that switches the field to free-text, so a brand-new model works out of the box without a table update. Efforts are the adapter-supported closed sets (claude/agy `--effort low|medium|high`; codex via the existing `--config model_reasoning_effort=<e>` degrade). **opencode is the deviant**: models are `provider/model` ids and effort is a `--variant` mapped to *user-configured* values, so its model and effort render as free-text with an inline **link to opencode's documentation** (`modelLink`); the validator must not reject a hand-typed opencode model or variant. When a role's `agent` changes the panel re-computes that role's option set (dropdowns are per-agent) and must never silently rewrite a saved value: an existing config value outside the table is preserved and shown as the selected "Other…" value — extending the existing `configFormOptions(...)` round-trip rule.
- **Document I/O with conflict detection.** A small `src/config/configDocument.ts` reads the raw file (text + parsed object + a conflict token derived from the file content, e.g. a sha256 of the text via `src/model/hash.ts` conventions or `crypto`) and writes atomically by reusing/exporting the existing `writeJsonAtomic` from `loadConfig.ts`. Save takes the token the panel loaded with; if the on-disk token differs the host refuses with a `conflict` error and the webview offers Reload / Overwrite. A `vscode.workspace.createFileSystemWatcher` on `.baiton/config.json` (same pattern as `specExplorer.ts`) posts `externalChange` so the panel can reload (automatically when the form is pristine, with a banner when it has unsaved edits).
- **Missing or corrupt config.** `loadConfig` already classifies `absent` / `unparseable` / `missing-section` / version errors; the panel reuses it for the semantic check but reads the raw document itself so it can preserve unknown keys. On `absent` or `unparseable` the webview renders an error state with the message and a **Reset to defaults** button that writes `defaultConfigJson()` (from `src/config/defaultConfig.ts`) after a modal confirmation, then reloads the form. Because `activate` in `src/extension.ts` returns early when the config is invalid, the command is registered unconditionally alongside `baiton.initialize` (before the config gate) so the reset path is reachable exactly when it is needed; it resolves the workspace the same way `runInitialize` does.
- **Save semantics.** The webview validates on every input and again on Save; the host re-validates the posted form (the webview is untrusted) before writing. Written JSON is two-space indented with a trailing newline, matching `defaultConfigJson()`. After a successful write the host applies the config live (see Live config reload above) and reports the outcome in the panel; where a component could not hot-reload, the post-save message names it instead of asking for a full Reload Window.
- **Command and view registration.** `package.json` gains the command (category Baiton, title "Open Config Panel") with no `when` clause (it must work before activation succeeds) plus the view/view-container contributions; `src/activation/commands.ts` exports a `registerConfigPanelCommand` next to `registerInitializeCommand`, and `extension.ts` registers it (and the view provider) before the config load.

## CLI model listing — follow-up investigation

A curated table is shipped now, but the executor should also **investigate whether each installed CLI exposes a models command** (`<bin> models`, `--list-models`, `doctor`, or help output) for claude, agy, codex and opencode. This is an investigation only: compile a small probe script, run the installed CLIs, and record what actually happens. If a CLI exposes a listing command, note in the README how a future change could fold that output into the capability probe (which already runs before every stage) so the curated table is refined automatically. Nothing in this change may depend on an unverified CLI surface — the shipped behaviour stays "curated table + Other…". Record the findings per agent even when the answer is "no such command".

## Testing
Host-free tests under `test/` (mocha + ts-node, existing conventions): validation and preservation of unknown keys (`test/configPanel.*.test.ts`), unit tests for `agentCapabilities` (per-agent shapes: enumerated models + efforts for claude/agy/codex; free-text shape for opencode), document I/O round-trip and conflict detection against a temp dir, and a controller test driven through `test/fixtures/vscodeLoader.mjs` in the style of `test/setApiKey.test.ts` covering load → edit → save, reject-invalid, and reset. A small test asserts the `contribues.views`/`contributes.viewsContainers` wiring in `package.json` and that the Open Config Panel command reveals the sidebar view. `media/config.js` mirrors the pure validator from the TS core the way `media/protocol.js` mirrors `webviewProtocol.ts`; keeping them in sync is asserted by a test that runs the same fixtures through both — extended so the mirror accepts/rejects the same opencode-style and "Other…" values as the TS core. Live-reload tests assert that after a save the shared config state and re-initialized consumers reflect the new values without a window reload, and that genuinely non-reloadable factors are reported in the save outcome.
