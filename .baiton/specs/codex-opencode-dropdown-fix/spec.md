# OVERVIEW

## Goal

Make the config panel's Codex, Claude, OpenCode and Antigravity model selectors current, valid dropdowns backed by live discovery, with per-model effort levels wherever the agent discloses them, while custom values stay selectable and editable as "Other…" entries and a failed, timed-out or malformed refresh keeps the last known-good list marked stale. This is the pending T16 of the model-selector-refresh spec, re-scoped from what the repository actually does today and widened to Claude and Antigravity.

## What is actually broken (read-only findings)

The discovery pipeline exists end to end (`Adapter.discoverModels` → `ModelDiscoveryService` → `CatalogStore` → `agentCapabilities(snapshots)` → `configFormOptions` → `optionsChanged` → `media/config.js`), but six seams are wrong or unconnected:

1. **The config panel never receives live capabilities.** `src/extension.ts` calls `registerConfigPanel({ capabilities: agentCapabilities() })` with the frozen builtin table and never passes `getCapabilities` / `onDidChangeCapabilities`; the `CatalogStore` and `ModelDiscoveryService` are built only afterwards. `RegisterConfigPanelDeps` and `ConfigPanelController` already support the live seam (the T15 end-to-end test wires it by hand), so in a real window every refresh lands in the store and the panel keeps showing the curated tables for every agent and the free-text OpenCode field. This is the root cause of "outdated Codex list", "outdated Claude list" and "OpenCode is a text input".
2. **The Codex `model/list` parser does not match the app-server reply.** `codexModelsFromAppServer` accepts `models` / `items` / bare array but not `result.data`; it prefers `id` over `model`; and `effortsFromSupported` reads `effort` / `id` / `name` on object elements while the app-server sends `{ reasoningEffort, description }`. The request also sends `params: {}` (no `includeHidden`, no `limit`, no `nextCursor` handling). A real reply therefore parses to `[]`, `discoverModels` resolves `undefined`, the service applies `err("codex model discovery returned no models")` and the builtin list is marked stale on every reload.
3. **Claude's curated table is wrong and its only discovery source is the network.** `CLAUDE_MODELS` is `claude-sonnet-5`, `claude-opus-5`, `claude-haiku-5`: `claude-haiku-5` does not exist (the CLI's id is `claude-haiku-4-5-20251001`) and the current `claude-opus-5-5` / `claude-fable-5-1` are missing. `CLAUDE_EFFORTS` is `low|medium|high`, but `claude --help` documents `--effort <low|medium|high|xhigh|max>`, so two valid levels can only be entered through "Other…". `ClaudeAdapter.discoverModels` reads only the models.dev `anthropic` provider, which carries no effort levels, and the service's claude job awaits the feed first, so offline the Claude list is always stale. Meanwhile the Claude CLI itself keeps an authoritative local catalog at `~/.claude/cache/model-catalog/<id>-cc.json` (`version: 2`, `fetchedAt`, `staleAt`, `catalog.surface: "cc"`, `catalog.config.models[]` with `id`, `name`, `section: main|overflow`, `thinking.type: effort|none`, `thinking.effort_options[] { id, name, badge?: { message: "Default" } }`). It lists every model the CLI's own picker shows, with per-model effort levels and the default level, and it needs no network or credential.
4. **OpenCode precedence is inverted and its effort levels are discoverable but never read.** `OpencodeAdapter.discoverModels` GETs `/api/model` first (starting an `opencode serve` child on every refresh) and only unions `opencode models` stdout afterwards. The requirement is `opencode models` primary, `/api/model` fallback when available. Separately, `OPENCODE_EFFORTS` is `[]` (free text) on the assumption that `--variant` values are unknowable, but they are not: `opencode models --verbose` (opencode 1.18.30) prints, after each `provider/model` line, that model's JSON including `variants: Record<string, object>` whose KEYS are exactly the values `--variant` accepts (`low`, `medium`, `high`, `xhigh`, `max`, `minimal`, `none`, `thinking`, …, per model). OpenCode computes the map itself from models.dev `reasoning_options` (effort values, `null` → `none`; budget → `high`/`max`; toggle → `none`/`high`), its per-package transform defaults, and the user's `provider.<id>.models.<id>.variants` config, so the CLI output is the only complete source. On this machine 26 of the 41 configured models carry a non-empty map; a model with `{}` has no reasoning levels. The bare listing carries none of this, `/api/model` returns `variants: []` for every model in this build, and the two server endpoints that do carry the map (`/provider`, `/config/providers`) also return the configured provider API keys in clear text, so they are unusable. OpenCode marks no default variant; a session with no variant (or the reserved literal `default`) runs with the provider's own default, which is what Baiton's empty `(default)` effort already produces (no `--variant` flag).
5. **Antigravity's model families and effort levels are hand-maintained although `agy models` discloses both.** `ANTIGRAVITY_MODELS` is a curated table (from agy 1.2.2) and the adapter has no `discoverModels`, on the recorded grounds that "a discovered id list could not carry the model+effort mapping". It can: `ModelEntry` carries per-model `efforts`. `agy models` (agy 1.2.12, about 1.5 s, needs the CLI's own sign-in) prints one `id<TAB>label` line per model on stdout (a spinner goes to stderr; exit code is 0 even on an error, so stdout must be judged, not the code), and Gemini effort levels are encoded as id suffixes: `gemini-3.8-flash-high|medium|low` ("Gemini 3.8 Flash (High)"), `gemini-3.1-pro-high|low`, while `claude-sonnet-4-6`, `claude-opus-4-6-thinking` and `gpt-oss-120b-medium` are fixed ids. agy confirms the same sets itself: `agy -p /effort --model gemini-3.1-pro` fails with `requires --effort (available: low, high)`, `--effort max` on `gemini-3.8-flash` fails with `has no "max" effort (available: low, medium, high)`, `--effort` on a Claude id fails with `--effort is not supported for model`, `gpt-oss-120b-medium` (and a bare `gpt-oss-120b`) answer `not adjustable`, and a bare family plus `--effort` (`gemini-3.8-flash --effort medium`) is accepted, which is exactly what `antigravityModelFlags` emits. The `--effort` help text's `low|medium|high|max` is the CLI-wide vocabulary; no listed model offers `max`. So the family table, the per-family levels and the fixed ids are all derivable from the listing, and the curated table is only ever as current as the last hand edit.
6. **Custom values are flattened into ordinary options.** `configFormOptions` appends a configured-but-unlisted model as a plain id in `models`, so the webview renders it as a normal dropdown option, not as an editable "Other…" entry; `AgentFormCapability` carries no `modelEntries`, so labels, per-model `efforts`, `defaultEffort` and `custom` markers (which `capabilitiesFromEntries` and `mergePreservingExisting` already produce) never reach the webview. The Codex, Claude, OpenCode and Antigravity per-model reasoning-effort metadata is lost at this seam.

Everything else needed already exists and is kept: `CatalogStore.applyResult` (failure keeps the previous list, sets `stale`/`staleReason`, persists), `overlayCapabilities` (an empty refreshed list never wipes a curated one; `claude-sonnet-5` is always present for claude; it already builds capability-level `efforts` from the union of per-entry efforts), `configFormOptions` round-tripping out-of-set agent/model/effort, the `optionsChanged` protocol message, the in-place `syncSelectOptions` and the sticky `otherModel` / `otherEffort` flags in `media/config.js`.

## Design

### 1. Codex: parse the real `model/list` reply (`src/adapter/codex.ts`)

- Send `model/list` with `params: { includeHidden: true, limit: <a reasonable page size, e.g. 100> }`; while the reply carries a non-empty `nextCursor` and the timebox has budget, send further `model/list` requests (new ids 3, 4, …) with `cursor` and concatenate the pages; a failed or timed-out follow-up page settles with the pages already received rather than `undefined`.
- `codexModelsFromAppServer` additionally accepts an object whose `data` is an array (preferred over `models` / `items`), takes the id from `model` first (then `id`, then `slug`), and `effortsFromSupported` additionally reads `reasoningEffort` on object elements. `defaultReasoningEffort` handling is unchanged. Hidden models are kept (the id is still valid to launch with).
- The handshake, JSONL framing, kill-on-every-path, timeout clamp and `undefined`-on-failure contract stay exactly as they are; the curated `CODEX_MODELS` / `CODEX_EFFORTS` remain the builtin fallback.

### 2. Claude: local model catalog first, models.dev fallback (`src/adapter/claude.ts`)

- New pure parser `claudeModelsFromCatalog(json: unknown): readonly ModelEntry[]`, total and never throwing. It accepts the `version: 2` shape above (and tolerates a missing `version` or `catalog.state`), requires `catalog.surface === 'cc'` (else `[]`), and maps each `catalog.config.models[]` element with a non-blank `id` starting with `claude-` to `{ id, label: name (when a non-empty string different from the id), efforts, defaultEffort }`: `efforts` is the ordered list of `thinking.effort_options[].id` when `thinking.type === 'effort'`, and `[]` when `thinking.type === 'none'` or absent; `defaultEffort` is the id of the option whose `badge.message` is `Default`, omitted when none. `section: main` entries come first in file order, then `overflow` entries in file order; both are valid `--model` values. Duplicate ids keep the first occurrence. No `custom` flag and no provenance fields.
- New injectable reader seam `readLocalCatalog(): Promise<unknown | undefined>` on `ClaudeAdapterOptions` (default: list `*.json` under `path.join(os.homedir(), '.claude', 'cache', 'model-catalog')`, parse each readable file, keep those with `catalog.surface === 'cc'`, and return the one with the largest numeric `fetchedAt`). Any I/O or parse error resolves `undefined`; the read is raced against `ctx.signal` and the same timebox as today. A catalog past its `staleAt` is still used: it is the CLI's own last-known-good list and is exactly what the CLI's picker shows.
- `discoverModels` precedence: the local catalog first; when it yields at least one entry that list is the result and no feed is read or fetched. Only when the catalog is missing, unreadable, malformed or empty does it fall back to `ctx.feed` / `fetchFeed` and `claudeModelsFromFeed` exactly as today (feed entries carry no per-model efforts). Both unusable → `undefined` ("keep the last known-good list"), never the curated list. `CLAUDE_REQUIRED_MODEL` is still guaranteed present exactly once. The result is built with `capabilitiesFromEntries(entries, { efforts })`, where `efforts` is the ordered union of the entries' own levels when any entry has them, else `CLAUDE_EFFORTS`.
- Curated fallback corrected: `CLAUDE_MODELS` becomes `claude-sonnet-5` (first, the `defaultConfig()` default), `claude-opus-5-5`, `claude-fable-5-1`, `claude-haiku-4-5-20251001`; `CLAUDE_EFFORTS` becomes `low|medium|high|xhigh|max` to match `claude --help`. `test/adapter.claude.test.ts` currently asserts `claude-opus-5-5` is absent from the curated list to prove discovery adds it; that assertion moves to an id the fixture carries and the curated list does not.
- `ModelDiscoveryService` keeps fetching the feed exactly once and handing it to the claude job as `ctx.feed`; no seam change. The adapter returns before touching the feed on the local-catalog path, so an offline window still refreshes Claude from the local catalog (the feed source itself is marked stale independently).
- Only ids, labels and effort names are read from the catalog file; no other field of it leaves the host. The launch argv (`--model`, `--effort`) is untouched.

### 3. OpenCode: `opencode models --verbose` first, `/api/model` fallback, per-model efforts from `variants` (`src/adapter/opencode.ts`)

- `discoverModels` runs `opencode models --verbose` first (within the shared budget; the existing 16 MiB `maxBuffer` covers the ~50 KB output, which takes about 1.5 s here). When it yields at least one `provider/model` entry, that list is the result and no server is started, no request is made.
- New pure parser `opencodeModelsFromVerboseOutput(stdout)`: after ANSI stripping, a line whose first token matches `OPENCODE_MODEL_TOKEN` starts an entry; the pretty-printed JSON object that follows (tracked by brace depth up to the matching close, ignoring braces inside strings) is parsed as that entry's detail; a block that fails to parse yields a plain `{ id, provider }` entry. From the detail it takes `label` = `name` (when a non-empty string different from the model id) and `efforts` = `Object.keys(variants)` in object order when `variants` is a non-null object with at least one key; a model with `{}`, a missing `variants`, or a non-object gets NO `efforts` key. No `defaultEffort` is ever emitted (OpenCode defines none). The plain-listing parser `opencodeModelsFromCliOutput` is kept: the verbose parser must produce the same ids from a bare listing, so an older CLI that ignores `--verbose` still yields ids without efforts.
- Only when the CLI is unavailable, fails, times out or yields nothing does it fall back to `/api/model`: a pre-existing server (`serverBaseUrl` / `OPENCODE_SERVER`) or one `opencode serve` child on loopback with an ephemeral port, disposed exactly once. `/api/model` yields ids and labels only (its `variants` is always empty in this build). `/provider` and `/config/providers` are never requested: both return provider API keys. `mergeOpencodeModelSources` is kept for the fallback (CLI entries, then API entries), or simplified accordingly.
- Both empty → `undefined` ("keep the last known-good list"), never the curated list. The result is built with `capabilitiesFromEntries(entries)` so the capability-level `efforts` becomes the ordered union of the entries' own levels (empty when no model carries any, which keeps today's free-text rendering); the builtin `OPENCODE_EFFORTS` stays `[]`, `modelLink` stays on the builtin, and provenance is still stamped by the store.
- Launch argv is untouched: a chosen effort is still passed as `--variant <effort>`, an empty effort still emits no flag. Baiton never emits `--variant default` (reserved by OpenCode to mean "no variant").

### 4. Antigravity: derive families and effort levels from `agy models` (`src/adapter/antigravity.ts`, `src/adapter/adapter.ts`, `src/orchestrator/modelCatalog.ts`)

- New pure parser `antigravityModelsFromCliOutput(stdout): readonly ModelEntry[]`, total and never throwing. After ANSI stripping, each non-blank line splits on the first tab into `id` and `label` (label optional). Ids are grouped by trailing level suffix `-<level>` where `<level>` is one of the CLI-wide vocabulary `low|medium|high|max` (`ANTIGRAVITY_EFFORT_VOCABULARY`, from `agy --help`). A family is formed only when two or more listed ids share the same stem with distinct level suffixes; the family yields one entry `{ id: <stem>, label: <label with its trailing " (<Level>)" removed>, efforts: [<levels in listing order>] }`. Every other id, including a lone suffixed id such as `gpt-oss-120b-medium` and every unsuffixed id, yields `{ id, label, efforts: [] }` (fixed: agy rejects `--effort` for it). No `defaultEffort` is emitted (agy defines none). Duplicates keep the first occurrence; blank ids are skipped. On today's listing this reproduces `ANTIGRAVITY_MODELS` exactly.
- `AntigravityAdapter.discoverModels(ctx)` runs `agy models` (`execFile`, `cwd: ctx.cwd`, raced against `ctx.signal`, bounded by `min(ctx.timeoutMs, DEFAULT_DISCOVERY_TIMEOUT_MS)`), ignores stderr and the exit code, parses stdout, and resolves `capabilitiesFromEntries(entries)` when at least one entry exists, else `undefined` (keep the last known-good list; never the curated table). Capability-level `efforts` becomes the ordered union of the families' levels (today `low, medium, high`). Nothing but ids and labels is read; no credential is touched (agy uses its own sign-in).
- `CatalogSourceId` gains `'antigravity'` (`CATALOG_SOURCE_IDS` order: claude, codex, opencode, antigravity, models.dev); `AGENT_CATALOG_SOURCE` gains `antigravity: 'antigravity'`; `ModelDiscoveryService` picks it up through the existing per-agent loop; `builtinAgentCapabilities().antigravity` gains `modelEntries` built from `ANTIGRAVITY_MODELS` (so the curated fallback also renders per-family efforts) and stays the seed. `overlayCapabilities` needs no antigravity special case. The doc comments in `antigravity.ts`, `adapter.ts` and `index.ts` that promise antigravity is never overlaid are rewritten; the tests that pin that promise (`test/adapter.index.test.ts` "antigravity is never overlaid" and "no adapter implements discoverModels yet; antigravity never will", `test/modelDiscovery.test.ts` "antigravity has no catalog source", the two `modelSelectorRefresh.test.ts` comments) are inverted to cover the overlay.
- `antigravityModelFlags` and the launch/attach argv are unchanged and keep validating against the curated `ANTIGRAVITY_MODELS`: a discovered family absent from the curated table passes through as `--model <family> --effort <level>` (which agy accepts, verified above) and agy reports its own `invalid model selection` for a bad pair. The curated table is refreshed by hand from the listing exactly as today; discovery only feeds the selectors.

### 5. Wire the live table into the config panel (`src/extension.ts`)

- Build the `CatalogStore` and `ModelDiscoveryService` before `registerConfigPanel`, and pass `getCapabilities: () => agentCapabilities(catalogStore.table())` and `onDidChangeCapabilities: (l) => discovery.onDidChange(() => l())` (returning the disposable). Keep `capabilities: agentCapabilities()` as the static fallback the controller already prefers last. `registerConfigPanel` and `ConfigPanelController` need no behavioural change; update the doc comment in `src/activation/configPanel.ts` that claims the wiring is a separate step.
- Ordering guarantee: the store is seeded (persisted `cached` snapshots or curated builtins) before the panel's first `load()`, so the first `loaded` already shows last known-good lists and every later `applyResult` reaches the open panel as `optionsChanged` without touching edits.

### 6. Carry rich entries and custom markers through the option merge (`src/config/configPanel.ts`, controller)

- `AgentFormCapability` gains optional `modelEntries: readonly { id; label?; efforts?; defaultEffort?; custom? }[]` (declared locally, mirroring `ModelEntry`, to keep the module import-free of adapter/orchestrator code). `configFormOptions` copies `modelEntries` from the capability (falling back to `{ id }` per model when absent) and, when it appends a form model that the list lacks, appends a matching `{ id, custom: true }` entry using the same rules as `mergePreservingExisting` (trim; skip blank, duplicate and already-present values; refreshed ids stay first, custom ones last). Appended out-of-set efforts stay in `efforts` as today. `models` keeps containing the custom id so `validateConfigForm`, the mirror validator, host-side re-validation and the existing round-trip tests are unchanged.
- `agentStaleness` is unchanged. `ConfigPanelController.refreshOptions()` / `load()` need no change beyond the richer options flowing through; the controller test gains cases for the entries/custom markers reaching `loaded` and `optionsChanged`. Only ids, labels, effort names and stale metadata cross to the webview.

### 7. Webview rendering (`media/config.js`, `media/config.html`)

- Dynamic model options are built from `modelEntries` when present: value = id, text = label (or id), and entries with `custom: true` are NOT rendered as ordinary options. A role whose model matches a custom entry (or is absent from the list) renders in the "Other…" state: the select shows "Other…", the text input is visible with the value and stays editable; the sticky `otherModel` flag keeps working. `syncSelectOptions` keeps its in-place, focus-preserving contract (compare by value and text).
- OpenCode: with a non-empty list the model control is the dropdown plus "Other…" exactly like the other agents, the documentation link stays visible, and the free-text input is shown only while the list is empty (first window before any snapshot).
- Per-model effort dropdown (Codex, Claude, OpenCode and Antigravity alike): when the selected model's entry carries `efforts`, the dynamic effort options are that model's list (an empty per-model list, e.g. Claude Haiku with `thinking.type: none`, leaves only the static default option); else the agent-level union. For OpenCode the effort control therefore becomes the same select plus "Other…" as the other agents whenever the agent-level union is non-empty, and stays a free-text input only while the union is empty; a model whose entry has no `efforts` key (no `variants`) shows the agent-level union so a manually typed `--variant` for it stays possible through "Other…". For Antigravity a fixed id (empty per-model list) leaves only the default option, and a family shows its own levels (e.g. `gemini-3.1-pro`: low, high). When the entry carries `defaultEffort`, the static `(default)` option reads `(default: <effort>)`. Validation stays against the agent-level union so a saved effort of another model is never rejected. Switching models re-syncs the effort options without resetting an "Other…" effort.
- Stale note unchanged ("stale — showing last known models"). The mirror block (`validateConfigForm`) is unchanged or updated in both places; `test/configPanel.mirror.test.ts` must still pass.

### 8. Fail-safe behaviour (no new mechanism; verified end to end)

A refresh that fails, times out or returns malformed data resolves `undefined` in the adapter, becomes `err(...)` in the service, and `CatalogStore.applyResult` keeps the previous `models`/`efforts`/`fetchedAt`/`source` with `stale: true` and a reason; `overlayCapabilities` never replaces a non-empty list with an empty one; `configFormOptions` re-appends configured values; the webview replaces options in place and shows the stale note. A stale or failed refresh never blanks a selector and never rewrites a custom value. The end-to-end suite (`test/modelSelectorRefresh.test.ts`) gains the Codex `data`-shaped reply, the Claude local-catalog path with per-model efforts and the offline fallback, the OpenCode CLI-first path, malformed-data staleness and the custom-as-Other… round-trip, and README's discovery section is corrected to describe the new sources, precedence and the Other… behaviour.

## Constraints honoured

- Specification only; the fix reuses the existing capability/discovery flow and `configFormOptions` merge; no ad hoc selector path.
- Codex, Claude, OpenCode and Antigravity launch/attach argv, permission mapping, session handling and ask-relay wiring are untouched (`antigravityModelFlags` still maps through the curated table); only the model sources, curated fallback tables and selector rendering change.
- Every curated table stays the builtin seed and fallback; an agent whose discovery fails keeps its last known-good list. Claude's discovered list always contains `claude-sonnet-5`.
- Discovery stays asynchronous, timeboxed, never awaited by activation, reads no secrets; the Claude local catalog is read only for ids, labels and effort names; the OpenCode verbose listing is read only for ids, `name` and `variants` keys, the `agy models` listing only for ids and labels, and the key-bearing `/provider` and `/config/providers` endpoints are never requested; webviews receive ids, labels, effort names and stale metadata only.
- Existing `.baiton/config.json` values round-trip unchanged; legacy/custom values (including a configured `claude-opus-5` or `claude-haiku-5` no longer in the list) are never silently rewritten or dropped and render as editable Other… entries.
