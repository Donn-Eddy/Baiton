## Risks

- Sub-agent chat transcripts of a spec-scoped parent live under .baiton/specs/<slug>/chat/ in the main checkout; they rely on GITIGNORE_CONTENTS ignoring specs/*/chat/, so makeRepo must commit .baiton/.gitignore or commitPaths/land dirty checks will sweep or refuse.
- The run id parser in BarrierFactory depends on the queue's default run id shape `<slug>-<todo>-<stage>-<attempt>-<time>`; if that changes, stage/todo inference breaks. Keep the slug free of stage words.
- The barrier assumes both sub-agents reach each stage; if one `run` call is refused (busy/illegal), the other waits for the 3s fallback and the test fails via releasedAlone — inspect the child transcripts' tool errors to diagnose.
- ScriptedClient chooses a sub-agent script from the task text in the first user message; if the runner prepends other user content, the /T0[12]/ match must target the task message specifically.
- The tool message field linking a result to its call (tool_call_id or similar) must be checked in src/orchestrator/modelClient.ts before keying parent results by call id.
- createRunPipeline in the alongside case runs with the spec branch checked out, not main; if the pipeline insists on the configured base or a clean status that counts the in-flight todo's state commit, the bug run may refuse — assert the actual base/branch it reports rather than hard-coding 'main'.
- createSpecDraftRunner with real ToolServices.git: the close path must commit nothing; if it does write, the main tree could become dirty and break the final clean-status assertion.
- Concurrent state commits through the shared writer and the two queues' git operations in worktrees can surface git index.lock contention in the main repo; a flaky failure here is a real defect in the writer serialization, not a test artifact.
- Timing: real git subprocesses make the main case slow; set this.timeout(30000) on the long cases.
