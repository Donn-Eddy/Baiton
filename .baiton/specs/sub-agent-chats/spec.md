# OVERVIEW

Let a chat spawn sub-agent chats, and make every spec stage run in an isolated per-todo worktree so several todos can be worked at the same time. Two halves, one spec: the chat half adds sub-agent chats (spawn, follow-up messages, forwarded questions, a read-only tree in the conversation browser); the isolation half changes how every spec stage executes so that concurrency is real — per-todo worktrees and branches, a central spec-branch writer, per-todo run queues and journals, and an explicit `land_todo` step before `submit_pr`. A sub-agent is another orchestrator chat (same provider/model, own tool loop, own transcript); the configured CLI harness agents still make every source change.

**Per-todo worktrees — `src/engine/todoWorktree.ts` (new), `src/git/`.** Every todo-level stage of a spec runs in `.baiton/worktrees/<slug>/<todoId>/` on branch `baiton/<slug>/<todoId>`, created from the spec branch's head the first time a stage is dispatched for that todo and reused by later stages until the todo lands. This mirrors `runWorktree.ts` (same `GitWorktreeService` primitives, same `Result`-not-throw style) but is keyed by slug+todo rather than run id: `todoWorktreeDirFor`, `todoBranchFor`, `createTodoWorktree` (idempotent: an existing registered worktree is reused), `findTodoWorktree`, `landTodoWorktree`, `removeTodoWorktree`, and `unlandedTodos(slug)` — the todos whose branch `baiton/<slug>/<id>` still exists. Landing merges the todo branch into the spec branch in the MAIN checkout: it refuses with a named reason when the spec branch is not checked out, the main tree is dirty outside the spec folder, or the branch is missing; a conflicting merge is aborted and the branch and worktree are left untouched; an up-to-date branch lands as a no-op; after a successful merge (message `spec(<slug>): land <todoId>`) the worktree and branch are removed. There is deliberately no `base-moved` check: the spec branch is expected to advance with state commits while a todo is in flight. A failed or stopped stage never removes the worktree or branch — they stay for inspection, exactly as a cancelled spec-less run keeps its worktree today. `GitService` gains `commitPaths(paths, message, trailers?)` (stage only the named paths, then commit) so central spec-folder commits never sweep unrelated changes, and the worktree service gains `listBranches(prefix)`.

**Central spec-branch writer — `src/engine/specBranchWriter.ts` (new), `src/activation/specStore.ts`, `src/engine/runQueue.ts`.** `spec.md` state, persisted stage artifacts and the per-todo journals are written only in the main checkout, on the spec branch, and only through one per-slug serialized writer: `createSpecBranchWriter({ specsDir, git })` exposes `apply(slug, fn)` which runs `fn` under an async lock per slug, so two todos' queues finishing at the same moment produce two state-box edits applied one after the other on freshly re-read content, each committed with `commitPaths(['.baiton/specs/<slug>'], 'spec(<slug>): <id> <what>')`. `SpecStore.writeState` and the queue's artifact persistence go through it; landing goes through it too, so a land can never interleave with a state commit. Nothing that runs inside a worktree ever touches the todo's state line: a stage's only writes are its `result.json` under the worktree's `.baiton/runs/<run-id>/` and (executor only) source files the queue commits on the todo branch.

**Per-todo run queues and journals — `src/engine/runQueue.ts`, `src/journal/`, `src/activation/engineFacade.ts`, `src/activation/commands.ts`, `src/engine/recovery.ts`.** The queue becomes per (slug, todo): `RunQueueDeps` gains `todoId`, a worktree seam and the spec-branch writer; `busy` means "a stage is already running for this todo", and there is no repo-wide serialization between todos any more. Each queue keeps its own journal at `.baiton/specs/<slug>/todos/<todoId>/runs.jsonl` (committed with the spec folder); the spec-level `runs.jsonl` remains for the spec-scoped stages (spec-draft, pr) and for specs that predate this change. A `readSpecJournal(specsDir, slug)` helper merges the spec-level file and every per-todo file so the facade's attempt/resume derivation, `latestExecuteCommit`, the plan Input_Rev lookup, the View command and crash recovery keep one reader. `launchAndComplete` runs the stage with `cwd` set to the todo's worktree (the brief, result and asks land under `<worktree>/.baiton/runs/<run-id>/`, so the role profiles' relative grants are unchanged); the drift check, the Execute commit (`spec(<slug>): <id> execute attempt <n>` with the `Run-Id:` trailer) and the post-run reset use a git service bound to the worktree; the clean-tree guard checks the worktree; artifacts (`plan.md`, `execute-<n>.md`, `review-<n>.md`) are still rendered into the main checkout's `todos/<id>/` folder and committed centrally. The Plan guard is extended: a todo may plan only when every `after` dependency is `done` AND landed (its branch is gone), refused as `deps-unlanded`, so a dependent todo's worktree always starts from a spec branch that contains its dependencies' work. The spec-draft runner and the spec-less run pipeline keep excluding each other as today and keep running in the main checkout; they no longer block per-todo stages. `commands.ts` caches queues by `<slug>/<todoId>`; Stop, View and `runningSlugs` address the per-todo queue.

**Landing and the PR gate — `src/orchestrator/controlTools.ts`, `src/orchestrator/seams.ts`, `src/orchestrator/toolServices.ts`, `src/engine/submitPr.ts`.** New top-level `drive` tool `land_todo(slug, todo)` (mutating, idempotent by call id, no confirm card — it is internal to the spec branch): refuses unless the todo is `done`, then lands through the `LandTodoSeam` and returns the merge commit (or `already landed` when no branch exists). Several todos may be reviewed before any lands; the parent lands in whatever order it decides. `submit_pr`'s readiness check additionally refuses while `unlandedTodos(slug)` is non-empty, naming them. The drive prompt's stage table becomes `pending → plan`, `planned → execute`, `executed → review`, `done (unlanded) → land_todo`, and `submit_pr` only when every todo is done and landed.

**Sub-chat sessions — `src/orchestrator/sessionStore.ts`.** A sub-agent chat is a child session stored beside its parent with no index file: `<scope dir>/<parentId>.children/<childId>.jsonl`, nesting once more for depth 2. `SessionMeta` gains `parentId?` and `depth`; the store gains `createChild`, `listChildren`, `listTree` (top-level sessions newest first, each followed by its descendants depth-first), and `pathFor` resolves nested ids; deleting a session deletes its children folder. A child's title derives from its first `user` record, which is the task the parent gave it.

**Registry surface, spawn tools and prompts — `src/orchestrator/registry.ts`, `src/orchestrator/guard.ts`, `src/orchestrator/controlTools.ts`, `src/orchestrator/systemPrompt.ts`.** Tools declare `phases` as today and the registry learns a second axis, `ToolSurface = 'top' | 'subagent'`: `definitionsFor(phase, surface)` / `assembleFor(phase, surface)` / `call(..., phase, surface)` advertise and run, for a sub-agent, exactly the read tools, `ask_user`, `run` (drive phase only) and the two spawn tools — never `draft_spec`, `approve_spec`, `submit_pr`, `land_todo`, `start_run`, `investigate` or the spec-write tools; only a top-level chat finishes a spec. `ToolContext` gains `caller?: { sessionKey, depth, phase, kind, signal }` so a tool knows who is calling it. Two new tools on every phase and both surfaces: `spawn_subagent(task)` returns `{ chatId, reply }` once the sub-agent's first turn ends, and `send_to_subagent(chat_id, message)` returns `{ reply }` for each follow-up; both go through a `SubAgentSeam`. A spawn from a caller at depth 2 is refused with a message naming the cap (`MAX_SUBAGENT_DEPTH = 2`); there is no cap on how many sub-chats run at once. `buildSubAgentPrompt(kind, phase, depth, specContent?)` states the sub-agent's role (do the task, report concisely, never finish a spec), the drive-phase run table when the parent is driving a spec, the same refusal and `ask_user` rules, and whether it may spawn.

**Concurrent tool calls — `src/orchestrator/toolLoop.ts`.** `Tool` gains `concurrent?: boolean`. Within one completion the loop runs every concurrent-flagged call in parallel and the rest one after another, and appends the `tool` results in the model's call order so the transcript and history are unchanged in shape; abort, round bound and the result cap behave as today. Read tools, `run`, `spawn_subagent` and `send_to_subagent` are flagged; `ask_user`, the spec-write tools, `approve_spec`, `land_todo` and `submit_pr` are not. This is what lets a parent (or a sub-agent) spawn several sub-agents — or drive several todos' stages — at once.

**Sub-agent runner — `src/orchestrator/subAgent.ts` (new).** A host-free `SubAgentRunner` owns the live sub-agents of one controller: `spawn` creates the child session, builds its prompt and tool surface, runs `runToolLoop` over the child's own history and transcript with a signal chained to the parent's, and resolves with the final assistant text; `send` re-enters the loop on the same child. It keys sub-agents by chat id, refuses a spawn beyond the depth cap, exposes `stopDescendants(parentKey)` (Stop on the parent aborts every descendant and declines their pending asks), and emits events (`started`, `delta`, `appended`, `finished`) the controller mirrors to the view. A sub-agent's `ask_user` is not answered by the parent: the runner wraps the intervention seam so the ask carries its origin (parent top-level session, child chat id), and the controller shows the card on the parent chat and persists the settled card to the parent transcript, with a system note on the child transcript recording the question and the answer.

**The user's view — `src/orchestrator/webviewProtocol.ts`, `media/protocol.js`, `media/chat.js`, `media/chat.html`, `src/activation/chatController.ts`, `src/activation/commands.ts`.** `SessionItem` gains `parentId?` and `depth`; `WebviewState` gains `readOnly` with a `setReadOnly` message; the reducer and the hand-mirrored `protocol.js` change together (the mirror suite enforces it). The session list renders children as collapsible rows beneath their parent (chevron on a parent that has children, collapse state kept in the webview). Selecting a child renders its transcript read-only: no composer, no answer controls on cards, no Stop, no delete. The controller posts live `streamDelta`/`appendMessage`/`updateTool` messages only for the session in view and re-renders from the transcript when the view switches, so watching a child stream while its parent runs works and switching back shows the parent's progress; while busy the user may select the running session or any of its descendants, and nothing else. Everything is on disk, so a window reload lists the same tree and reopens the session the user was in. `commands.ts` wires the `SubAgentSeam` into the tool services and the runner into the controller.

**Constraints.** No `vscode` import enters `src/orchestrator/`, `src/engine/`, `src/journal/` or `src/git/`; every new core is injectable and tested against temp repos or fakes, like its neighbours. Existing behaviour outside this scope is unchanged: a spec-less run, the spec-draft flow and the Auto-mode gates keep working, the parent's own `run` still drives plan → execute → review (now in a worktree) and then `land_todo`, transcripts stay append-only and backward compatible, and old specs with only a spec-level journal keep resuming. Tests are mocha under `test/`; `npm run compile`, `npm run lint` and `npm test` stay green after every todo.
